# V1 Components

## 1. Core Data Model (Postgres)
- Tables: connections, metric definitions (versioned), engines (versioned), jobs, results.
- Unique job/result key for idempotent writes.

### Invariants

**Explicit requirements**
- Exactly one result per job: a unique constraint on `results.job_id` means a retry or duplicate delivery can never create a second row.
- Metric definition and engine versions are immutable once registered: any edit creates a new version, and UPDATE/DELETE on published versions is rejected.
- Every job pins exact `metric_version_id`, `engine_version_id`, `connection_id` and its parameters at submission, and none of these can change afterward.
- Every result is traceable: result → job → pinned versions and parameters, with no nullable link in the chain.
- Job status follows a fixed state machine (`queued → running → succeeded | failed`, with `failed → queued` only on retry). Any other transition is rejected.
- Terminal `succeeded` implies a result row exists, and a result row implies the job is `succeeded`. Both are written in one transaction.
- Retries increment `attempt_count` and never exceed `max_attempts`. Past the limit the job stays `failed` permanently.
- Connection credentials are stored only encrypted and never appear in any API response, log line, or job record.

**Implied safeguards**
- Foreign keys are enforced everywhere, and versioned entities cannot be deleted while a job references them (`ON DELETE RESTRICT`).
- A `(metric_id, version_number)` pair is unique and gapless-increasing, and the same holds for engines. Concurrent registrations cannot produce duplicate version numbers.
- The job identity (`idempotency_key`) is unique, so resubmitting the same request returns the existing job instead of creating a new one.
- Status updates use optimistic locking or a compare-and-set (`WHERE status = expected`), so two workers cannot both claim the same job.
- A stale `running` job (lease or heartbeat expired) is reclaimable, so a crashed worker cannot strand a job.
- Parameters are stored as validated JSONB and a config hash is computed at submission, so the same inputs always produce the same hash.
- All timestamps are UTC and set by the database. `created_at` is immutable and `updated_at` is monotonic.
- Schema changes go only through Alembic migrations, and a test checks that migrations produce the same schema as the models.

## 2. Database Connector Layer
- Connector interface (connect, run query, validate).
- PostgreSQL connector (read-only).
- Credential storage and encryption.

## 3. Metric Registry
- Parameterized SQL templates (experiment id, date range, etc.).
- Versioning and safe parameter binding.

## 4. Statistical Engine Interface
- Standard input/output contract.
- Engine registry (versioned, user-registered Python engines).
- Reference engine: continuous and proportional metrics, treatment effect, SE, CI, p-value.

## 5. REST API
- Submit job, check status, fetch results.
- Register connections, metrics, and engines.
- Publishes jobs to Kafka.

## 6. Worker Service
- Kafka consumer: fetch data via connector, run engine, persist result.
- Retries, failure handling, dedup, status updates.

## 7. Infrastructure
- Dockerfiles per service (API, worker).
- Kafka and Postgres (local compose for dev).
- Kubernetes manifests: worker deployment, replicas, resource limits, restart and recovery.
- Basic logging and execution metrics.

## 8. Reference Implementation
- Synthetic experiment dataset and seed script.
- Sample SQL metric templates.
- End-to-end demo, including a swapped-in alternate metric, DB, and engine to prove extensibility.
